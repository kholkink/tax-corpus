# Налоговый ИИ-агент для юристов: архитектурный план

Цель: построить корпус налогового права РФ, пригодный для машинной работы, и поверх него — агента, который отвечает на вопросы налоговых юристов с точными ссылками на нормы в правильной редакции, разъяснения и практику.

Документ разбит на: принципы → границы → источники → модель данных → архитектура по слоям → агент → оценка качества → эксплуатация → фазы и сроки → риски → стек.

---

## 1. Принципы, которые нельзя нарушать

Эти решения определяют всё остальное. Если их принять позже — придётся переделывать.

1. **Время — первичная ось.** Единица хранения не «статья», а «структурная единица в конкретной редакции с интервалом действия». Любой запрос к корпусу имеет параметр `as_of_date`. Юристу нужна норма на дату операции, проверки или спора, а не «сейчас».
2. **Происхождение каждого фрагмента.** У каждого куска текста есть: источник (URL), дата получения, хеш, документ-первоисточник, положение в структуре. Без этого нельзя ни объяснить ответ, ни обновить корпус, ни отладить ошибку.
3. **Детерминизм важнее генерации.** Всё, что можно посчитать кодом (найти статью по номеру, сравнить редакции, взять ставку на дату, посчитать срок), делается кодом, а не моделью. LLM синтезирует и объясняет, но не «вспоминает» номера статей и ставки.
4. **Цитируй или откажись.** Агент не имеет права утверждать норму без ссылки на конкретный узел корпуса. Каждая цитата в ответе автоматически проверяется на существование и действие на дату. Если найти не удалось — агент говорит об этом явно.
5. **Числа живут в таблицах, а не в тексте.** Ставки, лимиты, сроки, коэффициенты хранятся структурированно с интервалами действия. Текст статьи — доказательство, таблица — рабочий источник.
6. **Узко и чисто лучше, чем широко и грязно.** Одна ошибка в отменённой норме обнуляет доверие юриста. Расширять покрытие только после того, как ядро проходит эталонный тест.
7. **Оценка качества с первого дня.** Эталонный набор вопросов и ожидаемых ссылок появляется до того, как написана первая строка агента. Каждое изменение корпуса и промптов гоняется через него.

## 2. Границы MVP

Налоговое право — удачный выбор: один кодекс как ядро, высокая ценность для практиков, очень сильная зависимость от дат (налоговая реформа 2025 года сделала это ещё острее), много структурированных данных (ставки, сроки, лимиты), где детерминированный подход даёт преимущество перед «просто чатом».

Рекомендуемая последовательность расширения:

| Этап | Покрытие | Почему |
|---|---|---|
| Ядро | НК РФ часть 1 целиком (администрирование, проверки, ответственность, сроки) | Нужна для любого вопроса, в любой отрасли налогов |
| Вертикаль 1 | Одна из: УСН + НПД + страховые взносы (малый бизнес) **или** НДС + налог на прибыль (корпоративный сегмент) | Малый бизнес: проще, массовый спрос, много типовых вопросов. Корпоративный: сложнее, дороже клиент, больше практики |
| Вертикаль 2 | НДФЛ (особенно после перехода на прогрессивную шкалу) | Пересекается с обеими аудиториями |
| Дальше | Имущественные налоги (регионы!), акцизы, НДПИ, международные соглашения | Требуют регионального слоя и отдельных источников |

Решение о первой вертикали принимать после интервью с 3–5 практикующими налоговыми юристами/бухгалтерами — по тому, какие вопросы они реально задают.

Что осознанно **не** входит в MVP: бухучёт (ПБУ/ФСБУ), таможенные платежи, валютное регулирование, региональные ставки для всех субъектов, полная арбитражная практика.

## 3. Источники и их свойства

### 3.1. Нормативный слой

| Источник | Что даёт | Особенности |
|---|---|---|
| **pravo.gov.ru** (Официальный интернет-портал правовой информации) | Официальные тексты законов и изменяющих законов, даты опубликования | Публикует акты в том виде, в каком они приняты (изменяющие законы — как «патчи»). Есть банк «Законодательство России» с редакциями — проверить глубину покрытия редакций НК и формат выдачи |
| **sozd.duma.gov.ru** | Законопроекты, пояснительные записки, стадии | Нужно для «что изменится» и для раннего предупреждения об изменениях |
| **publication.pravo.gov.ru** | Ежедневные публикации | Основа мониторинга изменений |
| **Постановления Правительства, приказы ФНС/Минфина** | Формы, форматы, перечни, коэффициенты-дефляторы | Приказы ФНС — на nalog.gov.ru и pravo.gov.ru; много PDF |

Важно: коммерческие системы (Консультант, Гарант) парсить нельзя — лицензии запрещают, а их консолидированные редакции и разметка — их интеллектуальный труд. Сами тексты законов авторским правом не охраняются (ст. 1259 ГК), но брать их нужно из первоисточников.

### 3.2. Разъяснительный слой

- **Письма Минфина и ФНС.** Ненормативные, но фактически применяются. Особенно ценны письма ФНС с пометкой «обязательно для применения налоговыми органами» и письма, направленные для использования в работе. Их сотни тысяч; противоречат друг другу; каждое привязано к дате и к редакции нормы, действовавшей на тот момент. Источники: nalog.gov.ru (раздел разъяснений), minfin.gov.ru.
- **Решения ФНС по жалобам** — публикуются на сайте ФНС, показывают позицию ведомства по конкретным спорам.

### 3.3. Судебный слой

- Постановления Пленума ВАС/ВС по налогам (в частности, по части первой НК и по необоснованной налоговой выгоде — они до сих пор цитируются наравне со ст. 54.1 НК).
- Обзоры практики ВС, определения Судебной коллегии по экономическим спорам.
- Постановления и определения Конституционного суда (ksrf.ru).
- Арбитражная практика (kad.arbitr.ru) — на этапе MVP только выборочно, по нужной вертикали и только кассация/ВС.

### 3.4. Справочный слой

КБК, ОКТМО, коды льгот и видов доходов, коэффициенты-дефляторы, региональные ставки (ФНС публикует справочную информацию по регионам), налоговый календарь, формы деклараций.

### 3.5. Неудобные факты об источниках

- Значительная часть — PDF, часто без текстового слоя (нужен OCR с проверкой).
- Изменяющие законы написаны как инструкции для человека: «в абзаце втором пункта 3 статьи 170 слова “…” заменить словами “…”». Применить их автоматически — отдельная задача.
- Отложенное вступление в силу, переходные положения, нормы «до 31 декабря 20XX года», обратная сила — всё это надо моделировать явно.

## 4. Модель данных

Хранилище — PostgreSQL как единая точка истины (структура + полнотекст + вектора через pgvector). Графовая БД не нужна на старте: граф ссылок умещается в таблицу рёбер с рекурсивными запросами. Переезд на Neo4j — только если появятся многошаговые обходы графа с миллионами рёбер.

### 4.1. Сущности

```
Act                    — акт: НК ч.1, ФЗ №…, Постановление Пленума №…
  act_id, kind (code|federal_law|gov_decree|fns_order|letter|court_act|…),
  official_number, adoption_date, publication_date, source_url, title

Edition                — редакция акта (снимок после применения изменения)
  edition_id, act_id, valid_from, valid_to (NULL = действующая),
  created_by_act_id (изменяющий закон), notes (переходные положения)

Unit                   — структурная единица: статья / пункт / подпункт / абзац
  unit_id (канонический, стабильный: nk2.ch21.art164.p3.sp1),
  act_id, parent_unit_id, kind, ordinal, label ("подпункт 1 пункта 3 статьи 164")

UnitText               — текст единицы в конкретном интервале
  unit_id, valid_from, valid_to, text, text_hash, source_edition_id
  (это главная таблица; всё остальное на неё ссылается)

Amendment              — атомарная правка из изменяющего закона
  amendment_id, amending_act_id, target_unit_id, operation (replace|insert|repeal|new_wording),
  raw_instruction, effective_date, status (auto_applied|manual|verified)

Reference              — ребро графа
  from_unit_id | from_act_id, to_unit_id | to_act_id, kind
  (cites|amends|interprets|applies|supersedes|defines_term|delegates_to),
  extracted_by (regex|llm|manual), confidence

Letter                 — письмо Минфина/ФНС
  letter_id, agency, number, date, subject, text, mandatory_flag,
  related_units[] (через Reference)

CourtAct               — судебный акт
  court, kind (plenum|review|ruling|decision), number, date, text,
  position_summary, related_units[]

Term                   — термин с определением (ст. 11 НК и отраслевые)
  term, definition_unit_id, valid_from, valid_to

Parameter              — структурированное число
  name (vat_rate_general, usn_income_limit, …), value, unit,
  valid_from, valid_to, conditions (jsonb), source_unit_id, region (nullable)

Snapshot               — версия корпуса
  snapshot_id, created_at, description, содержимое как неизменяемый набор
```

### 4.2. Битемпоральность

Для юриста важны две оси:
- **valid time** — когда норма действовала (для определения применимого права);
- **transaction time** — когда мы об этом узнали (для аудита: «почему вчера агент ответил иначе?»).

Минимум для MVP — valid time. Transaction time закрывается снимками корпуса (Snapshot) и неизменяемостью UnitText: правки не переписывают строки, а добавляют новые с новым интервалом.

### 4.3. Канонические идентификаторы

Идентификатор единицы не должен меняться при перенумерации соседей и при изменении текста. Правило: `<акт>.<путь по структуре>`; при добавлении статьи 164.1 она получает свой ID, а не сдвигает соседей. Все внешние ссылки (из писем, судебных актов, из ответов агента) резолвятся в эти ID.

## 5. Архитектура по слоям

```
┌─────────────────────────────────────────────────────────────┐
│ 7. Интерфейсы: чат для юриста, API, отчёт со ссылками        │
├─────────────────────────────────────────────────────────────┤
│ 6. Агент: понимание запроса → план → инструменты → синтез    │
│    → проверка цитат → ответ                                  │
├─────────────────────────────────────────────────────────────┤
│ 5. Инструменты (детерминированные API над корпусом)          │
├─────────────────────────────────────────────────────────────┤
│ 4. Индексы: BM25 + dense + метаданные + реранкер             │
├─────────────────────────────────────────────────────────────┤
│ 3. Граф знаний: единицы, редакции, ссылки, разъяснения,      │
│    практика, параметры                                       │
├─────────────────────────────────────────────────────────────┤
│ 2. Парсинг и консолидация: структура, редакции, ссылки       │
├─────────────────────────────────────────────────────────────┤
│ 1. Инжест: краулеры, OCR, дедупликация, сырое хранилище      │
├─────────────────────────────────────────────────────────────┤
│ 0. Оценка качества и наблюдаемость (пронизывает всё)         │
└─────────────────────────────────────────────────────────────┘
```

### Слой 1. Инжест

- Краулеры по источникам с уважением к robots.txt и ограничением частоты; каждый документ сохраняется в сыром виде (HTML/PDF) в объектное хранилище с хешем, URL, датой.
- OCR (Tesseract с русской моделью или более сильные модели) для PDF без текстового слоя; результат помечается как OCR с оценкой качества.
- Дедупликация по хешу и по содержанию (одно письмо публикуется в нескольких местах).
- Мониторинг: ежедневный проход по публикациям pravo.gov.ru и nalog.gov.ru; новые документы попадают в очередь на обработку.

### Слой 2. Парсинг и консолидация

Самый трудоёмкий слой. Три подзадачи:

**a) Структурный парсер.** Разбивает текст на иерархию. Подход: набор правил (регулярные выражения по маркерам «Статья N.», «N.», «N)», абзацы) + валидация (номера идут по порядку, нет пропусков, вложенность корректна). Всё, что не проходит валидацию, — в очередь на ручную/LLM-разметку с обязательной проверкой человеком. На кодексе типовые проблемы: статьи с дробными номерами, «утратил силу», примечания, таблицы, части без нумерации.

**b) Консолидация редакций.** Два пути, использовать оба:
- Взять готовые редакции из первоисточника (банк «Законодательство России» на pravo.gov.ru), если формат позволяет надёжно извлечь редакции на дату — это основной путь.
- Построить применитель патчей: парсер изменяющих законов, распознающий типовые операции («изложить в следующей редакции», «дополнить пунктом», «слова … заменить словами …», «признать утратившим силу»). Автоматически применяются только операции с однозначной привязкой; остальное — вручную. Результат сверяется с готовыми редакциями там, где они есть, — это одновременно тест парсера.

Для НК число изменяющих законов — сотни; полная ручная верификация нереальна, но для MVP нужна лишь глубина 3–5 лет по выбранной вертикали плюс текущая редакция части 1.

**c) Извлечение ссылок.** Регулярные выражения покрывают явные ссылки («пункт 3 статьи 164 настоящего Кодекса», «Федеральный закон от … № …-ФЗ»). Неявные («в порядке, установленном Правительством», «законодательство о бухгалтерском учёте») — извлекать LLM-ом с указанием confidence и не использовать в автоматических выводах без проверки.

### Слой 3. Граф знаний

Собирается из слоёв 1–2 и разъяснительного/судебного контента. Ключевые связи для налогов:
- `interprets`: письмо/пленум → единица НК (с датой; письмо может быть привязано к устаревшей редакции — это надо показывать).
- `defines_term`: ст. 11 НК и отраслевые определения → термин.
- `parameter_of`: параметр (ставка, лимит) → единица-источник.
- `transition`: переходное положение изменяющего закона → затронутые единицы.

Отдельная задача — **извлечение параметров**: пройти по вертикали и выписать все числа с условиями и интервалами действия. Делается полуавтоматически (LLM предлагает, человек подтверждает), результат — самая ценная таблица в системе.

### Слой 4. Индексы

- Чанк = структурная единица (пункт/подпункт) с контекстом заголовков: «НК РФ, часть 2, глава 21 НДС, статья 164 Налоговые ставки, пункт 3». Не резать по токенам — юрист мыслит статьями.
- Гибридный поиск: BM25 (полнотекст PostgreSQL или отдельно) + dense-эмбеддинги (многоязычная модель, помещающаяся в 8 ГБ VRAM) + фильтры по метаданным (акт, дата, тип документа). Слияние через RRF, затем кросс-энкодер-реранкер.
- Индекс всегда фильтруется по `as_of_date`: искать только среди единиц, действовавших на дату.
- Отдельные индексы для писем и судебных актов с полями «связанные единицы» — чтобы от найденной нормы одним шагом расширяться в разъяснения.

### Слой 5. Инструменты агента

Детерминированные функции, каждая возвращает структурированный результат с ID и цитируемым текстом:

```
get_unit(unit_id, as_of_date)              — текст единицы на дату
resolve_citation("п. 3 ст. 164 НК")         — строка → unit_id
search(query, as_of_date, filters)          — гибридный поиск
diff_editions(unit_id, date_a, date_b)      — что изменилось
list_amendments(unit_id, since)             — история правок и кем внесены
get_interpretations(unit_id, as_of_date)    — письма/пленумы по норме
get_parameter(name, as_of_date, region)     — ставка/лимит/срок
compute_deadline(event, date, rules)        — расчёт срока по правилам ст. 6.1 НК
get_transitions(act_id)                     — переходные положения
```

### Слой 6. Агент

Пайплайн обработки запроса:

1. **Понимание запроса.** Извлечь: налог/режим, субъект (ИП/ООО/физлицо), период/дату событий, юрисдикцию (регион, если релевантно), тип вопроса (норма / расчёт / риск / процедура). Если даты нет — спросить или явно принять «текущая дата» и написать об этом.
2. **Планирование.** Какие инструменты вызвать: обычно `resolve_citation`/`search` → `get_unit` → `get_interpretations` → при необходимости `get_parameter`, `diff_editions`.
3. **Сбор контекста** с расширением по графу: норма → определения терминов → разъяснения → практика → переходные положения.
4. **Синтез.** Сильная модель формирует ответ строго в формате: вывод → обоснование с цитатами → противоречия/риски (если письма расходятся с практикой) → что изменилось (если вопрос затрагивает границу редакций) → уровень уверенности.
5. **Проверка цитат.** Каждая ссылка в ответе парсится, резолвится в unit_id и проверяется на действие на дату. Несуществующие или недействующие — ответ отправляется на переработку или помечается.
6. **Отказ.** Если релевантных норм не найдено или уверенность низкая — честный ответ «в корпусе нет достаточных оснований», а не додумывание.

Разделение моделей: сильная API-модель для планирования и синтеза; локальная 7–8B для дешёвых массовых задач (классификация писем, извлечение ссылок, черновая разметка).

### Слой 7. Интерфейсы

Чат с обязательным блоком «Источники» (кликабельные ссылки на текст единицы в нужной редакции), переключатель даты, просмотр diff редакций, экспорт ответа в документ. API для интеграции в системы юрфирм.

## 6. Оценка качества

Без этого проект превращается в демо.

**Эталонный набор.** 150–300 вопросов от практиков по выбранной вертикали, для каждого: ожидаемые нормы (unit_id + дата), ожидаемые разъяснения, краткий эталонный вывод, «ловушки» (вопрос про прошлый период, вопрос про отменённую норму, вопрос с региональной спецификой).

**Метрики.**
- Citation precision/recall: доля правильных ссылок среди приведённых / доля ожидаемых ссылок, которые найдены.
- Temporal correctness: доля ответов с правильной редакцией на дату.
- Hallucination rate: ссылки на несуществующие/недействующие нормы (должно быть ~0 благодаря проверке).
- Abstention quality: правильно ли агент отказывается, когда оснований нет.
- Retrieval metrics отдельно от генерации (recall@k по unit_id), чтобы понимать, где ломается.

**Процесс.** Каждое изменение корпуса, индекса, промптов — прогон эталона в CI. Ответы на ловушки читаются человеком. Ежемесячно — ревью 30–50 реальных запросов юристом.

## 7. Эксплуатация

- **Обновления.** Ежедневный мониторинг → очередь новых документов → парсинг → ручная проверка сложных правок → новый снимок корпуса → прогон эталона → публикация. Юристам виден номер снимка и дата актуальности.
- **Наблюдаемость.** Логи каждого запроса: план, вызовы инструментов, найденные единицы, финальные цитаты, результат проверки. Это и отладка, и аудит, и материал для расширения эталона.
- **Безопасность и право.** Персональные данные в судебных актах (152-ФЗ) — обезличивать при инжесте. Запросы юристов — конфиденциальны: не отправлять в сторонние API без соглашения или использовать локальные модели для чувствительного сегмента. Явный дисклеймер: система — инструмент для юриста, а не юридическая консультация.
- **Версионирование.** Корпус, промпты, модели эмбеддингов — всё версионируется совместно; при смене эмбеддера полная переиндексация со снимком.

## 8. Фазы и сроки (1–2 человека, без полной занятости первое время)

**Фаза 0 — Постановка (2 недели).**
Интервью с юристами, сбор 100+ реальных вопросов, выбор вертикали, первичный эталон (50 вопросов), проверка доступности редакций на pravo.gov.ru (это влияет на объём фазы 1). Результат: документ границ и эталон v0.

**Фаза 1 — Ядро корпуса (5–7 недель).**
Инжест pravo.gov.ru, структурный парсер, модель данных, консолидация части 1 НК и главы(глав) вертикали на текущую дату + 3 года истории, канонические ID, извлечение явных ссылок. Результат: БД с проверенными текстами, тест «покажи п. X ст. Y на дату Z» проходит на эталоне.

**Фаза 2 — Граф и разъяснения (3–4 недели).**
Пленумы и обзоры ВС по вертикали, письма Минфина/ФНС за 3–5 лет с привязкой к единицам, термины, таблица параметров с интервалами. Результат: от любой нормы за один запрос видны разъяснения и практика на дату.

**Фаза 3 — Поиск и агент (4–5 недель).**
Индексы, инструменты, агентный пайплайн, проверка цитат, интерфейс. Прогон эталона, итерации до целевых метрик (ориентир: citation precision > 0.95, temporal correctness > 0.95 на эталоне). Результат: рабочий MVP для пилота с 2–3 юристами.

**Фаза 4 — Пилот и расширение (постоянно).**
Реальные запросы → расширение эталона → вторая вертикаль → региональный слой → арбитражная практика → автоматизация обновлений.

Итого до пилота: ~4 месяца при плотной работе, 6+ при частичной занятости.

## 9. Риски и как их гасить

| Риск | Последствие | Мера |
|---|---|---|
| Редакции на pravo.gov.ru не извлекаются надёжно | Фаза 1 удлиняется вдвое | Проверить в фазе 0; иметь применитель патчей как запасной путь; ограничить глубину истории |
| Ошибка консолидации → агент цитирует отменённую норму | Потеря доверия | Двойная проверка (готовые редакции vs патчи), эталонные «ловушки», обязательная проверка цитат |
| Письма Минфина противоречат друг другу и практике | Неверный вывод | Хранить все позиции с датами, показывать конфликт явно, приоритет: КС > ВС > пленум > письмо ФНС «обязательное» > письмо Минфина |
| Переходные положения реформы 2025 | Много «особых случаев» | Моделировать transition явно как единицы с интервалами и связями |
| PDF без текста, битый OCR | Тихие искажения текста | Оценка качества OCR, выборочная сверка, приоритет HTML-источникам |
| Лицензии коммерческих баз | Юридическая проблема | Только первоисточники; фиксировать provenance |
| Персональные данные в практике | 152-ФЗ | Обезличивание на инжесте |
| Галлюцинации номеров статей | Критическая ошибка | Резолвер цитат + отказ при неудаче; модель никогда не «вспоминает» номера |
| Стоимость сильной API-модели на длинных контекстах | Экономика | Жёсткий отбор контекста реранкером, локальные модели для черновых задач, кэширование |

## 10. Рекомендуемый стек

- **Язык:** Python 3.12.
- **Хранилище:** PostgreSQL 16 + pgvector + полнотекстовый поиск (или отдельный OpenSearch, если BM25 в Postgres окажется слабым на русской морфологии); объектное хранилище для сырых файлов (MinIO/S3).
- **Парсинг:** lxml/BeautifulSoup, регулярные выражения, pdfplumber/PyMuPDF, Tesseract (rus) для OCR.
- **Эмбеддинги/реранкер:** многоязычные модели уровня bge-m3 / multilingual-e5 и bge-reranker — помещаются на RTX 3070 Ti в fp16/int8; при масштабировании — выделенный сервер или API.
- **LLM:** сильная API-модель для синтеза; локальные 7–8B (квантованные) через vLLM/llama.cpp для классификации и извлечения.
- **Оркестрация:** на старте — простые скрипты и Makefile; при росте — Prefect/Dagster для пайплайнов инжеста.
- **Агент:** свой тонкий слой над function calling без тяжёлых фреймворков — контроль над каждым шагом важнее.
- **Оценка:** pytest + собственный harness над эталоном; отчёты по метрикам в CI.
- **Интерфейс:** FastAPI + простой веб-клиент; позже — интеграции.
