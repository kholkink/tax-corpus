# План ПО: реализация продуктовых фич поверх tax-corpus

Версия 1, 10.09.2026. Основание: `docs/architecture-plan.md` (корпус и агент, слои 0–7),
`docs/workspace-plan.md` (рабочее пространство, фазы A–B готовы), `docs/product-features.md`
(15 фич в трёх уровнях). Здесь — как именно это строится: целевая архитектура, платформенные
работы, спецификация каждой фичи (данные, модули, инструменты, API, UI, тесты, оценка),
последовательность, команда, риски.

Правило плана: ничего не переписывать. Каждая фича — расширение существующих модулей с
теми же инвариантами: `as_of` во всех запросах, провенанс у каждого фрагмента, детерминизм
там, где можно посчитать кодом, проверка цитат в каждом ответе и файле, снимок корпуса.

## 2. Спецификации фич

Формат каждой: цель → данные → модули и функции → инструменты агента → API → UI → тесты и
оценка → оценка трудоёмкости → зависимости → риски.

### F1. Аудит документа

**Цель.** Загрузить любой юридический текст (меморандум, возражения, консультацию, свой или
чужой) и получить отчёт по каждой ссылке: существует, действует на дату, изменилась ли после
даты документа, какие письма по ней сняты с применения, чего не хватает.

**Данные.** Таблица `audit(audit_id, workspace_id?, source_path|text_sha256, as_of, doc_date,
report jsonb, created_at, created_by)`. Без изменений схемы корпуса.

**Модули.** `tools/audit.py`:
- `audit_text(text, as_of, doc_date=None) -> AuditReport` — объединяет `citations.extract_citations`
  (нормы), `interpretations.verify_doc_citations` (письма/пленумы), `references.RE_FEDERAL`
  (ФЗ), резолв, статус OK/STALE/MISS/PART, для OK — `changed_since_doc` по `amendment.effective_date`
  > `doc_date`, `outdated_letters` (письма по норме со статусом outdated, на которые документ
  опирается), `missing_context` (обязательные письма ФНС по цитируемым нормам, не упомянутые).
- `render_html(report, text)` — исходный текст с подсветкой ссылок и всплывающим статусом.
- `render_markdown(report)` — таблица для файла дела.

**Инструменты агента.** `audit_document(path)` в workspace: отчёт как результат + файл
`research/аудит-<имя>.md`.

**API.** `POST /audit` (text или base64-файл, as_of, doc_date) → report; `GET /audit/{id}.html`.
`POST /workspaces/{slug}/audit` для файлов дела.

**UI.** Страница «Аудит»: загрузка/вставка текста, дата документа, отчёт со сводкой (N ссылок,
K проблем), подсвеченный текст, экспорт md/html.

**Тесты и оценка.** Юнит: синтетический документ с OK/STALE/MISS/изменившейся нормой/снятым
письмом. Эталон: 10 реальных документов (обезличенных) с ручной разметкой ссылок → точность и
полнота обнаружения ссылок ≥ 0.95.

**Трудоёмкость.** 1–2 недели. **Зависимости.** Нет. **Риски.** Извлечение цитат в нестандартной
форме («абз. 2 п. 3 ст. 170 Кодекса» уже есть; «ст. 170 (п. 3)» — расширить регэкспы по эталону).

### F2. Мониторинг дела

**Цель.** Дело автоматически следит за нормами и документами, на которые опирается его
позиция; изменение → уведомление и новая версия ресёрча с разделом «что изменилось для вашего
периода».

**Данные.**
```sql
corpus_event(event_id, kind, unit_id, doc_id, payload jsonb, detected_at, snapshot_id)
  -- kind: unit_text_changed | unit_repealed | document_added | document_status_changed
  --       | parameter_changed | edition_published
subscription(subscription_id, workspace_id, unit_id, doc_id, article_id, origin_path, created_at)
notification(notification_id, workspace_id, event_id, status open|seen|applied, created_at)
```
Подписки выводятся автоматически из шапок файлов `research/` и `drafts/` (`sources`), плюс
предки на уровне статьи; юрист может добавить вручную.

**Модули.** `jobs/monitor.py`:
- `detect_events(prev_snapshot, new_snapshot)` — diff по `unit_text.text_hash` на unit_id,
  по статусу документов, по новым документам с их рёбрами; результат — `corpus_event`.
- `match_subscriptions(events)` → `notification`.
- `apply_to_workspace(notification)` — запускает сессию агента в деле с системной задачей:
  «обновить <файл> с учётом события», агент пишет новую версию через `write_file` с
  `triggered_by=event_id`; секция «Что изменилось» строится детерминированно из
  `diff_editions`/`list_amendments`/новых документов, модель только формулирует последствия.
- Источники событий: ежедневные задачи `crawl_fns`, `crawl_minfin`, `crawl_courts`,
  `check_bank_editions` (сравнение списка редакций банка с загруженным), `embed_new`.

**Инструменты.** `list_notifications(workspace)`, `what_changed(unit_id, since)`.

**API.** `GET /workspaces/{slug}/notifications`, `POST …/notifications/{id}/apply`,
`GET /events?since=`. **UI.** Колокольчик в деле; список событий с diff текста единицы
(старая/новая редакция) и версий файла (`.versions/` уже есть).

**Тесты.** Синтетика: два снимка с изменённым пунктом → событие → подписка → уведомление →
применение с подменным клиентом; проверка, что новая версия файла содержит diff-секцию.

**Трудоёмкость.** 2–3 недели после P1, P3. **Зависимости.** P1, P3; полная ценность — с F3.
**Риски.** Шум событий (косметические правки текста банком) — порог по diff, игнор пометок.

### F3. История редакций и машина времени

**Цель.** Норма на любую дату за 3–5 лет по выбранным главам, diff между датами, переходные
положения.

**Данные.** `unit_text` уже интервальная. Добавить: `amending_act(act_id, official_number,
adoption_date, publication_date, source_url, text)`, расширить `amendment`: `instruction_text`,
`operation` (replace|insert|repeal|replace_words|insert_words|delete_words|renumber),
`target_unit_id`, `target_position` (абзац/после слов), `effective_date`, `applied_status`
(auto|manual|verified|failed), `diff jsonb`. `edition` получает `created_by_act_id`.
`transition(act_id, unit_ids[], text, applies_from, applies_to)`.

**Модули.** `corpus/patcher.py`:
- парсер инструкций изменяющих законов (грамматика: «в пункте 3 статьи 170 слова “…”
  заменить словами “…”», «дополнить пунктом 3.1 следующего содержания:», «изложить в
  следующей редакции:», «признать утратившим силу», «абзац второй исключить»);
- применение к дереву единиц на `effective_date` → новые строки `unit_text` с интервалами;
- «round-trip»-проверка: база + все патчи до сегодня = текущий текст банка; расхождения → очередь
  сверки (`applied_status=failed`) с UI редактора.
- Источник текстов изменяющих законов: publication.pravo.gov.ru (официальные публикации,
  HTML/PDF), список законов и НГР-номеров — из шапки консолидированного текста банка (уже
  извлечены в `amendment.amending_act_number`).
- Даты вступления: из текста закона («вступает в силу по истечении одного месяца…») +
  `compute_deadline`; неоднозначные — вручную.

**Инструменты.** `diff_editions(unit_id, date_a, date_b)` (текстовый diff + список правок),
`get_transitions(act|unit_id, as_of)`, `get_unit` без изменений.

**API/UI.** `GET /units/{id}/history`, `GET /units/{id}/diff?a=&b=`; в UI у нормы — лента
редакций и переключатель даты; страница «Очередь сверки» для редактора (принять/исправить патч).

**Тесты и оценка.** Юнит на каждую операцию грамматики; интеграция: ч. 1 НК за 2023–2026
round-trip без расхождений по выбранным главам; эталон-ловушки «норма на дату Z» (уже есть
формат as_of в эталоне) — 30 вопросов по прошлым периодам.

**Трудоёмкость.** 6–8 недель (грамматика 2, применитель 2, инжест законов 1, сверка и UI
редактора 2), поэтапно: сначала ч. 1 + гл. 21 + 26.2 на 3 года.
**Зависимости.** P2, P3. **Риски.** Самый высокий: нестандартные формулировки, таблицы,
приложения; мера — доля автоматически применённых патчей как метрика (цель ≥ 85 %), остальное
руками редактора; сверка с текстом банка как истина.

### F4. Карта позиций по норме

**Цель.** Для нормы — позиции Минфина, ФНС (обязательные отдельно), пленумов, ВС, КС по датам
и статусу, с явными конфликтами и указанием, к какой редакции нормы относится позиция.

**Данные.** `document` расширить: `court`, `case_number`, `outcome` (taxpayer|authority|mixed|
n/a), `topics text[]`. Новая `position(position_id, doc_id, unit_id, stance pro_taxpayer|
pro_authority|neutral, summary, quote, extracted_by llm|manual, confidence, verified bool,
verified_by, edition_at (дата редакции нормы на момент документа))`.

**Модули.** `jobs/crawl_courts.py`: обзоры и определения ВС (vsrf.ru, раздел «Практика» и
обзоры), акты КС (ksrf.ru), пленумы ВАС/ВС (arbitr.ru, vsrf.ru) — расширение
`fetch_court_acts.py` до списочного краулера с провенансом. `knowledge/positions.py`:
- `extract_positions(doc)` — дешёвая модель по каждому ребру `interprets`: stance + краткая
  формулировка + цитата из документа (цитата проверяется на точное вхождение — детерминизм);
- `conflicts(unit_id, as_of)` — группировка по stance с приоритетом источников и датами;
- пометка «относится к прежней редакции», если `document.date` < последняя `effective_date`
  правки единицы.

**Инструменты.** `get_position_map(unit_id, as_of)` → структура для агента и UI;
`get_interpretations` дополняется stance.

**API/UI.** `GET /units/{id}/positions?as_of=`; вкладка «Позиции» в карточке нормы: три колонки
(за налогоплательщика / за налоговый орган / нейтрально), фильтры по источнику и дате, отметка
«проверено редактором».

**Тесты и оценка.** Эталон позиций: 50 документов с ручной разметкой stance → точность
извлечения ≥ 0.85, иначе показываем без stance. Проверка точной цитаты — 100 %.

**Трудоёмкость.** 3–4 недели (краулеры 1–2, извлечение и конфликты 1, UI 1).
**Зависимости.** P3, P4 (дешёвый профиль модели). **Риски.** Доступность vsrf/ksrf для
краулера (паузы, повторы уже есть); качество stance — редакторская проверка.

### F5. Калькуляторы с цитатами

**Цель.** Детерминированные расчёты, где каждый шаг ссылается на пункт НК, по образцу
`compute_deadline`.

**Данные.** `parameter` пополняется: `key_rate` (ключевая ставка ЦБ с интервалами, источник
cbr.ru), лимиты и суммы штрафов из ст. 119, 122, 126, 129.1 с якорями.

**Модули.** `tools/calculators.py`:
- `compute_penalty(amount, due_date, paid_date, taxpayer_kind)` — ст. 75: ставка 1/300 и
  1/150 по правилам на дату периода, с учётом моратория/особых периодов из корпуса (переходные
  положения → F3);
- `compute_fine(article, base, mitigating=[], aggravating=[])` — ст. 112, 114 (уменьшение не
  менее чем вдвое), ст. 119/122/126;
- `appeal_deadlines(event, date)` — возражения на акт (п. 6 ст. 100), апелляция (ст. 139.1),
  жалоба (ст. 139), обращение в суд (АПК — внешний акт, помечается);
- `limitation_status(offense_date, as_of)` — ст. 113.
Каждый результат: значение, шаги, `applied_units`, предупреждения (неполный календарь и т. п.).
Правила берутся из текста корпуса и подтверждаются якорями в тестах (как `test_parameters_terms`).

**Инструменты.** `compute_penalty`, `compute_fine`, `appeal_deadlines`, `limitation_status`.
**API/UI.** `POST /calc/{name}`; страница «Калькуляторы» с формами и шагами расчёта.

**Тесты.** Числовые примеры из разъяснений ФНС/Минфина (в реестре) как эталонные случаи;
якорные проверки формулировок.

**Трудоёмкость.** 2–3 недели. **Зависимости.** инжест ключевой ставки (P3). **Риски.** Особые
периоды (мораторий 2022–2023) без F3 задаются вручную в `parameter` с интервалами.

### F6. Факты и таймлайн дела

**Цель.** Из документов дела — таблица фактов с источником (файл, страница, цитата), таймлайн
событий, автоматические сроки и задачи.

**Данные.** `workspaces/<slug>/facts.json` + таблица `fact(fact_id, workspace_id, kind
date|amount|party|event|period|regime, value, text, source_path, page, quote, extracted_by,
confirmed bool)`.

**Модули.** `tools/facts.py`: `extract_facts(workspace, paths)` — модель предлагает факты,
код проверяет, что `quote` дословно есть в тексте файла (иначе факт отклоняется), даты и суммы
нормализуются; `timeline(facts)`; `derive_deadlines(facts)` через F5 → задачи.
**Инструменты.** `list_facts`, `add_fact`, `confirm_fact`. Системный промпт дела: факты —
только из подтверждённой таблицы или файлов.
**API/UI.** `GET/POST /workspaces/{slug}/facts`; вкладка «Факты» (таблица, правка, подтверждение)
и «Таймлайн».
**Тесты.** Синтетический акт проверки в docx → факты с точными цитатами; отклонение факта без
цитаты. **Трудоёмкость.** 2 недели. **Зависимости.** F5 для сроков. **Риски.** OCR сканов —
Tesseract с оценкой качества (план §1), низкое качество → факты только вручную.

### F7. Шаблоны документов и экспорт DOCX

**Цель.** Черновики документов по шаблонам фирмы с автозаполнением фактов и проверенными
цитатами; экспорт в DOCX.

**Данные.** `templates/<firm>/<name>.md` с плейсхолдерами `{{facts.date_of_act}}` и секциями
для агента; реестр шаблонов в БД (`template`). **Модули.** `workspace/templates.py` (рендер
плейсхолдеров из фактов, секции агента через write_file), `workspace/export.py` (markdown →
DOCX через python-docx: заголовки, списки, таблицы, сноски-источники; шапка провенанса —
в свойства документа и последнюю страницу). **Инструменты.** `draft_document(template, path,
facts)`. **API.** `GET /workspaces/{slug}/files/{path}?format=docx`, `GET /templates`.
**UI.** Кнопка «Экспорт DOCX», выбор шаблона при создании черновика.
**Тесты.** Рендер шаблона, DOCX открывается (zipfile + XML-проверка), цитаты в шаблоне проходят
проверку. **Трудоёмкость.** 2–3 недели. **Зависимости.** F6. **Риски.** Оформление фирмы —
делать через стили docx-шаблона (reference docx), а не вручную.

### F8. Совместная работа

**Цель.** Несколько юристов на деле, комментарии к файлам агента, роли, журнал.
**Данные.** P5 + `comment(comment_id, workspace_id, path, version, anchor (номер абзаца),
author, text, created_at, resolved)`, `activity(workspace_id, actor user|agent, action, target,
at, details)`. **Модули.** `api/auth.py`, `workspace/collab.py`; агент видит комментарии как
инструмент `list_comments(path)` и учитывает их при обновлении файла; сессии привязаны к
пользователю. **API.** CRUD комментариев, `GET …/activity`, приглашения. **UI.** Боковая панель
комментариев с привязкой к абзацу, лента активности, присутствие.
**Тесты.** Права (viewer не пишет), комментарий → агент отвечает в новой версии.
**Трудоёмкость.** 3 недели. **Зависимости.** P1, P5. **Риски.** Конфликты версий — файлы
агента версионируются, файлы юриста редактируются вне системы (синхронизация папки), конфликт
решается «последняя версия + история».

### F9. Уровни конфиденциальности

**Цель.** Дело выбирает, куда уходят данные; чувствительные дела — локальная модель; явная
плашка.
**Данные.** `workspace.confidentiality standard|sensitive`, `provider_profile` в конфиге
(P4). **Модули.** `agent/providers.py`: выбор профиля по делу и задаче; `workspace/redact.py`:
детерминированная маскировка ИНН/паспортов/ФИО/счётов перед отправкой в облачный профиль
(словарь замен хранится в деле, ответ де-маскируется). Локальный профиль: LiteLLM-прокси с
Anthropic-совместимым входом → vLLM (Qwen/Llama 7–8B, план §10) на GPU-машине.
**API/UI.** Поле при создании дела; бейдж «данные: облако DeepSeek / локально» в шапке дела и в
каждом ответе. **Тесты.** Маскировка/демаскировка round-trip; чувствительное дело не создаёт
запросов к облачному профилю (подменный клиент). **Трудоёмкость.** 1–2 недели + инфраструктура
GPU. **Риски.** Качество локальной 8B-модели ниже — компенсируется детерминированными
инструментами и проверкой цитат; для чувствительных дел допускаем «медленнее, но локально».

### F10. Региональный слой

**Цель.** Ставки и льготы субъектов (УСН, имущество, транспорт, земля) как параметры с
регионом. **Данные.** `parameter.region` (код субъекта), `regional_act` (закон субъекта,
источник pravo.gov.ru региональный раздел). **Модули.** `jobs/crawl_regions.py`: справочный
сервис ФНС по ставкам и льготам (структурированный источник) → параметры с интервалами и
ссылкой на региональный закон. **Инструменты.** `get_parameter(name, region)` уже принимает
регион; `list_regional_benefits(region, tax)`. **UI.** Регион в манифесте дела; параметры
показывают регион. **Тесты.** 5 регионов × 3 налога с якорями. **Трудоёмкость.** 2–3 недели.
**Риски.** Формат сервиса ФНС меняется — краулер с тестом на структуру.

### F11. Публичная карта точности

**Цель.** Измеримое доверие: метрики по темам на эталоне из 150–300 вопросов, обновляемые
автоматически.
**Модули.** Эталон v1: интервью с 3–5 практиками, сбор вопросов, разметка ожидаемых норм через
инструменты корпуса (как v0), ловушки; `evaluation.py` — разрез по темам (тег вопроса);
`jobs/eval_nightly` с бюджетом; `reports/accuracy.md` + `GET /accuracy` для сайта. Публикуем:
citation precision/recall, hallucination, temporal, abstention по темам и дате снимка.
**Трудоёмкость.** инфраструктура 1 неделя; сбор эталона — 3–4 недели календарных с юристами.
**Зависимости.** P8. **Риски.** Разброс модели на малой выборке — ≥ 150 вопросов и 3 прогона.

### F12. Объяснимость

**Цель.** Понятно, почему найдено и что показано. **Модули.** `search`: возвращать источники
попадания (lexical/dense/письмо-ссылка) и совпавшие леммы — уже есть `sources`, добавить
`matched_terms`; карточка нормы в UI: текст на дату, лента правок (`list_amendments`), письма и
позиции (F4), история версий (F3). **Трудоёмкость.** 1–2 недели UI. **Зависимости.** F4/F3 для
полноты.

### F13. Реранкер и эмбеддинги

**Цель.** Поднять recall@5 с 21/23 и качество на длинных вопросах. **Модули.** `search/rerank.py`:
кросс-энкодер (bge-reranker-v2-m3) над top-30 гибрида; эмбеддинги bge-m3 на GPU; pgvector в
проде (`unit_embedding(unit_id, model, vec)`), npz — для разработки. **Оценка.** `eval_search`
на эталоне v1; латентность ≤ 1 с на запрос на GPU. **Трудоёмкость.** 1 неделя (+ GPU).

### F14. Международный контур

**Цель.** СИДН, МЛИ, комментарии как отдельные акты с тем же провенансом. **Модули.** парсер
структуры договоров (статьи/пункты, две языковые версии) — вариант `parser.py` с грамматикой
договора; `act.kind=treaty`, код `sidn-<iso>`; резолвер цитат «ст. 10 СИДН с Кипром».
**Трудоёмкость.** 3–4 недели. **Риски.** Даты применения/приостановления (указы 2023) — как
интервалы действия акта.

### F15. Интеграции

**Цель.** Документы попадают в дело без ручной перекладки. **Модули.** `jobs/intake_email`
(IMAP → inbox/), ICS-экспорт задач и сроков, импорт xlsx (оборотки), ЭДО (Диадок API) —
входящие требования; ЛК ФНС — ручной импорт (публичного API нет). **Трудоёмкость.** 2–3 недели
на первый набор.

## 4. Нефункциональные требования

- **Латентность.** Ответ агента ≤ 30 с на типовой вопрос (сейчас 15–30 с), поиск ≤ 300 мс
  (лексика) / ≤ 1 с (гибрид с реранкером на GPU). Кэш промпта (уже включён) и кэш эмбеддингов
  запросов.
- **Стоимость.** Учёт токенов по делу (P6); дешёвый профиль для извлечения (позиции, факты),
  сильный — для синтеза; бюджет вызовов в промпте (уже есть).
- **Безопасность.** Секреты только в `.env`/vault; токены API; роли; журнал действий; файлы дел
  вне git; маскировка ПДн; шифрование бэкапов; 152-ФЗ — хранение в РФ (self-hosted).
- **Надёжность.** Идемпотентные загрузки (уже), снимки корпуса до/после инжеста, откат к
  снимку; краулеры с повторами и resume (уже).
- **Совместимость.** Провайдер модели заменяем (Anthropic-совместимый API); Windows/WSL/Linux
  (уже).

## 5. Риски и меры

| Риск | Вероятность | Мера |
|---|---|---|
| Грамматика изменяющих законов не покрывает формулировки (F3) | высокая | метрика авто-применения, очередь сверки, поэтапный охват глав, сверка с текстом банка |
| Источники блокируют краулеры (nalog, minfin, vsrf) | средняя | паузы, повторы с ростом, узнаваемый UA, инкрементальность, кэш сырья |
| Модель перецитирует (precision ~0.5) | средняя | эталон v1 для калибровки промпта, реранкер, оценка по темам, «цитируй только основания» |
| Малая выборка эталона даёт шумные метрики | высокая | ≥ 150 вопросов, 3 прогона, доверительные интервалы в отчёте |
| Локальная модель слабее облачной (F9) | средняя | детерминированные инструменты + проверка цитат; честная плашка «медленнее, но локально» |
| Рост схемы без миграций ломает прод | средняя | P2 до любых изменений в Q4 |
| Юридические ограничения источников | низкая | только первоисточники, провенанс, запрет коммерческих баз (план §3.1) |
