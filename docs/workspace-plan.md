# Рабочее пространство налогового юриста: план надстройки над корпусом

Цель: превратить корпус и агента в среду совместной работы (cowork) юриста и агента над
конкретным делом. У дела есть папка с файлами, агент читает и создаёт файлы, ведёт
ресёрч с проверяемыми цитатами, задаёт уточняющие вопросы и ждёт ответа, юрист
дополняет материалы и направляет работу. Всё, что агент утверждает о нормах, по-прежнему
проходит проверку цитат, а в файлах остаётся провенанс.

Принципы основного плана сохраняются: время как ось (у дела есть `as_of`), провенанс,
детерминизм, «цитируй или откажись», оценка качества.

---

## 1. Что уже есть и что переиспользуется

| Есть | Как используется в workspace |
|---|---|
| Инструменты слоя 5 (search, get_unit, get_parameter, get_interpretations, compute_deadline …) | без изменений, тот же `TOOL_DEFINITIONS` |
| Агент с ручным циклом tool use и проверкой цитат (`agent.py`, `citations.py`) | цикл расширяется файловыми инструментами и инструментом вопроса пользователю; проверка цитат применяется и к файлам, которые пишет агент |
| API (`api.py`) | добавляются ресурсы workspace / files / sessions |
| Реестр разъяснений, снимки корпуса | ответы и памятки ссылаются на номер снимка |
| Журнал вызовов и оценка (`evaluation.py`) | журнал сессии = тот же формат; эталон пополняется задачами из реальных дел |

Провайдер модели: сейчас DeepSeek через Anthropic-совместимый API; архитектура не зависит
от провайдера. Managed Agents Anthropic (готовые сессии с контейнером и файлами) подошли бы
идеально, но требуют ключа Anthropic; при его появлении сессионный слой можно заменить на них,
инструменты корпуса остаются нашими.

## 2. Модель данных

```
Workspace  — дело/клиент
  workspace_id, slug, title, client, as_of (дата, на которую берутся нормы),
  jurisdiction (регион, если важно), created_at, tags
  папка: workspaces/<slug>/
    workspace.json            — манифест (поля выше + настройки)
    inbox/                    — загруженное юристом (docx, pdf, xlsx, txt, md)
    notes/                    — заметки юриста (md), редактируются руками
    research/                 — материалы агента: <тема>.md с блоком «Источники» и отчётом проверки
    drafts/                   — черновики документов агента (памятка, возражения, запрос)
    sessions/<session_id>.json — история диалога (messages + журнал вызовов + проверки)
    index/                    — индекс текстов дела для поиска агентом (по файлам inbox/notes)

File       — файл в workspace
  path, sha256, size, mime, uploaded_by (lawyer|agent), created_at, version,
  text_extracted (bool), sources (для файлов агента: unit_id/doc_id + отчёт проверки)

Session    — один разговор в рамках дела
  session_id, workspace_id, started_at, status (active | waiting_user | done),
  messages[] (полная история для модели), tool_log[], open_questions[]

Question   — вопрос агента пользователю (инструмент ask_user)
  question_id, session_id, text, options[] (необязательно), asked_at, answer, answered_at
```

Хранение: файлы на диске (простой обмен с юристом: папка синхронизируется чем угодно),
метаданные — те же таблицы в PostgreSQL (`workspace`, `workspace_file`, `session`,
`session_question`), чтобы API и снимки видели их. Версии файлов агента: каждая запись
создаёт новую версию, старая не перезаписывается (как `unit_text`).

## 3. Инструменты агента (добавляются к слою 5)

```
list_files(path?)                         — дерево файлов дела с размерами и датами
read_file(path, page?/range?)             — текст файла (docx/pdf/xlsx/md/txt), большие — постранично
search_files(query)                       — поиск по документам дела (лексический + e5 на CPU)
write_file(path, content, sources[])      — создать/обновить файл в research/ или drafts/;
                                            цитаты внутри проверяются, отчёт проверки пишется в шапку
append_note(path, text)                   — дописать в заметку (например, протокол решений)
ask_user(question, options?)              — задать уточняющий вопрос; сессия переходит в
                                            waiting_user, цикл прерывается до ответа
create_task(title, due?)                  — поставить задачу юристу (собрать документ, уточнить факт)
```

Правила в системном промпте: файлы в `inbox/` и `notes/` агент не изменяет; факты дела берутся из
файлов, нормы — из корпуса; в каждый файл агента записываются `as_of`, номер снимка корпуса
и список источников; персональные данные из документов не переносятся в ресёрч без нужды.

`ask_user` реализуется как обычный инструмент: цикл агента, встретив вызов, сохраняет сессию со
статусом `waiting_user` и возвращает управление. Ответ юриста подаётся как `tool_result`
этого вызова, история продолжается без потери контекста (как в цикле переработки сейчас).

## 4. Сценарии

1. **Новое дело.** Юрист создаёт workspace, кладёт в `inbox/` акт проверки и договоры,
   пишет в `notes/задача.md` вопрос. Агент: читает файлы, извлекает факты и даты, задаёт
   2–3 уточняющих вопроса (`ask_user`), ищет нормы и разъяснения, пишет
   `research/позиция.md` с выводом, обоснованием, рисками, «что изменилось» и источниками.
2. **Дополнение.** Юрист добавляет письмо инспекции в `inbox/`, пишет заметку. Агент в той же
   сессии обновляет `research/позиция.md` (новая версия), помечает, что изменилось.
3. **Сроки.** Агент считает сроки по ст. 6.1 от дат из документов и ставит задачи с датами.
4. **Черновик документа.** По просьбе юриста агент готовит `drafts/возражения.md` по шаблону,
   юрист правит руками, агент по запросу сверяет цитаты в правленом тексте (`verify`).

## 5. Интерфейс

Фаза A — CLI/REPL: `python -m taxcorpus workspace new|open <slug>`, диалог в терминале,
вопросы агента выводятся и ждут ввода, файлы в папке. Минимум кода, проверяемо тестами.

Фаза B — веб-клиент над API: список дел, дерево файлов с просмотром, чат сессии с блоком
«Источники» (клик открывает норму в нужной редакции), карточки открытых вопросов и задач,
переключатель `as_of`. Один статический фронт (без сборки) поверх FastAPI.

Фаза C — совместная работа: несколько юристов на деле, комментарии к файлам агента,
экспорт в DOCX, шаблоны документов фирмы, интеграция с почтой/календарём.

---

## 6. Извлечение текста из файлов

docx — как в краулере Минфина (zipfile + XML, без сторонних библиотек); pdf с текстовым
слоем — `pypdf`; сканы — OCR (Tesseract rus) с пометкой качества, как в плане §1; xlsx —
`openpyxl` в таблицу markdown. Всё извлечённое кэшируется рядом с файлом (`.text.md`) с sha256
источника: повторно не извлекается, изменение файла видно.

---

## 7. Качество и безопасность

- Проверка цитат — обязательна для ответов и для файлов агента; в шапке файла отчёт
  (OK/STALE/MISS) и дата `as_of`.
- Эталон дел: 10–20 модельных дел с файлами и ожидаемыми выводами; метрики те же плюс
  «нужные факты извлечены из файлов» и «уточняющие вопросы уместны».
- Персональные данные: файлы дела не покидают workspace; в ресёрч попадают только нужные факты;
  запросы к модели идут с настроенным провайдером (сейчас DeepSeek — это надо явно
  показывать юристу как условие конфиденциальности; при чувствительных делах — локальная модель).
- Права: пока один пользователь; в фазе C — роли и аудит действий по сессиям.

## 8. Порядок работ

1. **A1.** Модель workspace/файлов/сессий, извлечение текста (docx/pdf/txt/md), индекс дела.
2. **A2.** Инструменты list/read/search/write/append/ask_user/create_task; расширение агента
   персистентной сессией и режимом `waiting_user`; проверка цитат в файлах.
3. **A3.** CLI-диалог по делу; тесты с подменным клиентом (сценарий 1 целиком).
4. **A4.** API: workspaces, files (upload/download), sessions (start/message/answer), questions.
5. **B.** Веб-клиент.

Оценка: A1–A3 — 2–3 дня плотной работы, A4 — 1 день, B — 3–5 дней.
